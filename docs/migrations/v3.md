# Migration: v2 to v3 — declarative database roles

v3 adds `addRole()`: a way to provision additional database accounts, with grants,
on top of a database created by `createDatabase()`. It is now a **required** method
on `IDatabaseInstance`, implemented by all three backends (CloudNativePG, MariaDB,
Neo4j), and `createDatabase()` itself is reimplemented on top of the same role
provisioning code each backend uses for `addRole()`. That reuse is why this is a
major version: the method being required is a breaking change for anyone who
implements `IDatabaseInstance` directly (test mocks, mainly — no in-repo call site
needed updating), and one existing default flips behaviour on upgrade (see
`superuserAccess` below).

For everyone only *calling* `createDatabase()` today, without implementing the
interface, the upgrade does not change what gets created in the database or
Kubernetes for existing databases. The new surface is additive.

## What changed, per engine

Grants are the part that differs most between engines, because only one of the
three models privileges as a CRD:

| | CloudNativePG | MariaDB | Neo4j (Community) |
| --- | --- | --- | --- |
| `addRole()` mechanism | `DatabaseRole` CR + a `psql` Job for grants | `User` CR + one `Grant` CR per grant | one-shot `cypher-shell` Job |
| `grants` | Job runs as the **database owner**, never superuser; one transaction revokes everything the role holds, then re-grants the desired set | declarative `Grant` CRs, reconciled continuously | **throws** — Community edition has no RBAC |
| `login: false` | supported | **throws** — every MariaDB account is a login account | **throws** — every Neo4j account is a login account |
| `environments` on `createDatabase()` | supported | supported | **throws** — Community allows a single user database |
| `config.owner` override | supported | **throws** unless it equals the database name — `User.spec.name` is immutable | supported |
| `reclaimPolicy` | consumed (`DatabaseRole.spec.databaseRoleReclaimPolicy`) | ignored (documented, not silently dropped) | ignored (documented, not silently dropped) |
| `objects: "all"` on a grant | `GRANT ... ON ALL TABLES IN SCHEMA` **and** `ALTER DEFAULT PRIVILEGES FOR ROLE <owner> ...`, so future tables are covered too | `table: "*"`, which already covers tables created later | n/a |

Adding a role with the same name as the database's owner throws on every engine —
the owner's `DatabaseRole`/`User` CR (or Job, on Neo4j) is already created by
`createDatabase()`; a second one would fight the first over the same account's
password. Role names containing a backtick, single quote, double quote,
backslash, or NUL byte are rejected on every engine as well, since all three embed
the name in a quoted identifier somewhere downstream (SQL, Cypher, or a CR field).

See [API Reference](../api-reference.md#dbaddrolename-config) for the full
`addRole()` signature, the `IDatabaseRoleConfig` / `IDatabaseGrant` / `IDatabaseRole`
shapes, and one worked example per engine.

## The upgrade

For a stack that does not call `addRole()` yet, the upgrade is unattended:

```bash
npm install
pulumi up
```

Nothing needs to be renamed or aliased by hand — see "The alias guarantee" below.
Adding roles afterward is opt-in: call `db.addRole(...)` wherever you need an
additional account.

## Pre-flight: `migrate v3`

Before upgrading, run the read-only checker bundled with the CLI:

```bash
npx @reyemtech/nimbus migrate v3
```

It never mutates anything — no `kubectl apply/patch/delete`, no `pulumi up`, no
file writes. It checks, in order:

1. **CNPG CRDs** — that `databases.postgresql.cnpg.io` and
   `databaseroles.postgresql.cnpg.io` are installed. The only check that can FAIL
   and drive a non-zero exit code; everything else is informational.
2. **Role attributes vs. the nimbus baseline** — for every CNPG cluster it can
   reach, compares each role's `pg_roles` attributes against
   `login=t, super=f, createdb=f, createrole=f, inherit=t, connlimit=-1, bypassrls=f, memberof={}`.
   A role that deviates (hand-granted `CREATEDB`, membership in another role, a
   connection limit) will have that attribute forced back to the baseline the next
   time its `DatabaseRole` CR reconciles.
3. **Database ownership** — flags any database whose owner doesn't match the
   nimbus default-owner convention (owner name equals database name), as a nudge
   to confirm it against an explicit `owner` in your Pulumi config, not a hard
   failure.
4. **`-superuser` Secret consumers** — greps the working tree for references to
   the `{cluster}-superuser` Secret, since `superuserAccess` defaulting to `false`
   deletes it (see below).

Exit code is `1` only if the CRD check fails; everything else prints `WARN` and
still exits `0`. Review the warnings before running `pulumi up`.

## `superuserAccess` now defaults to `false`

`IOperatorClusterConfig.superuserAccess` (CloudNativePG only) used to default to
`true`. It now defaults to `false`. On an existing cluster this is the one part of
the upgrade that is not purely additive: CNPG responds to
`enableSuperuserAccess: false` by setting the `postgres` role's password to NULL
and deleting the `{cluster}-superuser` Secret. Databases and roles created through
`Database`/`DatabaseRole` CRDs never needed that Secret — the operator's instance
manager reconciles them locally — so nothing inside nimbus reads it once the CRDs
are in place.

If something outside nimbus does connect as `postgres` over the network, opt back
in explicitly before applying:

```typescript
operator.createCluster("pgsql-main", {
  superuserAccess: true,
});
```

`migrate v3`'s fourth check exists specifically to surface out-of-band consumers
of that Secret before you find out the hard way.

## The alias guarantee

Every Pulumi logical resource name that existed before this branch was reviewed
against what the new code produces, and pinned by tests. Running `pulumi preview`
against an already-provisioned stack should show **zero `replace` operations** —
no database, role, or connection Secret is recreated, and no password rotates.
Verify this before running `pulumi up`:

```bash
pulumi preview --diff
```

Two things do change in Pulumi state without being destructive:

- **Neo4j provisioning Jobs are replaced once.** `spec.template.spec.containers[0].command`
  is an immutable Kubernetes field, and the Job's command text changed slightly: a
  second `cypher-shell` statement, `GRANT ROLE reader, editor TO ... || true`, is
  gone. It was Enterprise-only and failed — silently, because of the `|| true` —
  on every Community deployment, so removing it changes nothing about what the Job
  actually accomplished. Kubernetes replaces the Job rather than patching it, once,
  on the first `pulumi up` after upgrading. This is harmless: the surviving
  `CREATE USER ... IF NOT EXISTS` statement skips an account that already exists,
  and the replacement Job reads its password from the same Secret the connection
  Secrets were replicated from, so the two cannot diverge.
- **The `Secret.get()` read-back on MariaDB and Neo4j gets a new logical name.**
  Both backends now share the same credential-handling code CloudNativePG already
  used, and that code derives the read-back resource's name from the primary
  Secret's name in a way that doesn't match the ad-hoc name each backend used
  before. This is safe and needs no alias: `Secret.get()` registers an **external**
  resource — Pulumi never claims ownership of it — so dropping the old name from
  state only prunes a state entry; it issues no `Delete` against the live Secret.

If `pulumi preview` shows a `replace` on anything other than a Neo4j provisioning
Job, stop and investigate before applying — that would mean a password is about to
rotate.

## Known limitation: `ALTER ROLE ... SET`

There is no way to reach `ALTER ROLE <role> SET <guc> = <value>` (for example,
`default_transaction_read_only = on`) through `addRole()`. The grant-reconciliation
Job runs as the database owner, and PostgreSQL only lets a non-superuser alter its
own session defaults, not another role's — and `IDatabaseRoleConfig` has no field
for a GUC in any case. In practice this rarely matters: granting `pg_read_all_data`
(via `engineOptions.postgresql.inRoles`) already restricts a role to `SELECT`, so
read-only access is enforced by privilege rather than by session default. If you
need the GUC itself, either set `superuserAccess: true` and run the `ALTER ROLE`
by hand, or manage that one role outside nimbus.

## Rollback

`reclaimPolicy` defaults to `"retain"` on every role and database it applies to
(CloudNativePG only — MariaDB and Neo4j ignore it), so removing an `addRole()`
call from your Pulumi program and running `pulumi up` deletes the CR but leaves
the underlying account and its privileges in place. To restore superuser access,
set `superuserAccess: true` again — CNPG regenerates the `postgres` password and
recreates the `{cluster}-superuser` Secret.

## Verification checklist

- [ ] `npx @reyemtech/nimbus migrate v3` reviewed — no unexplained WARNs, no FAIL
- [ ] `pulumi preview --diff` shows zero `replace` operations (aside from an
      expected one-time Neo4j provisioning Job replacement)
- [ ] Application credentials still authenticate after `pulumi up`
- [ ] Anything found referencing a `-superuser` Secret has been migrated off it,
      or `superuserAccess: true` was set for that cluster
